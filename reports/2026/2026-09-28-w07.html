任务一：FastAPI Route 与请求/响应

4 小时
P0FastAPI L2 · HTTP L2

用途：把只能在脚本里运行的 AI 逻辑变成其他程序可以通过 HTTP 调用的稳定接口。Route 决定地址和方法，Request Schema 约束输入，Response Schema 约束输出。

  1. 运行最小 FastAPI 应用，使用 GET /health 返回健康状态。
  2. 定义 ChatRequest 与 ChatResponse，实现 POST /chat。
  3. 先用固定字符串或本地函数验证接口，再接已有 LLM / Agent Demo，避免同时 Debug 多层问题。
  4. 在 /docs 中检查 OpenAPI 自动文档，分别提交有效和无效请求。
  5. 确认 API Key 只从环境读取，不写入代码、日志或公开仓库。

这项任务怎么学

对应资料：FastAPI First Steps、Request Body、Response Model。

主导方法：AI 中文讲清 Route / Method / Schema → 官方文档核对最小写法 → 你先写固定响应 → 再接已有 AI 函数 → 用交互文档检查。

验收：GET /health 和 POST /chat 可运行；有效输入得到符合 Schema 的响应；能解释 Request、Response 与普通 Python 函数参数/返回值的关系。

内部拆分：概念与官方示例 0.75h；Request / Response Schema 1h；接入已有逻辑 1.5h；手动调用与整理 0.75h。

学习建议：先让接口返回固定结果再接模型；否则网络、模型、Schema 和服务启动错误混在一起，定位成本很高。

任务二：异常、ValidationError 与状态码

2.5 小时
P0错误边界 L2

用途：API 的可靠性不仅是“成功时能返回”，还要让调用方知道哪里错了、该不该重试、错误是否来自输入。

  1. 构造缺字段、类型错误或越界输入，观察 FastAPI 自动校验响应。
  2. 为一个确定的业务条件抛出 HTTPException，例如请求的资源不存在。
  3. 记录 2xx、4xx、5xx 的基本含义；本周只掌握 Demo 直接使用的少量状态码。
  4. 确保错误响应不暴露密钥、内部路径或完整堆栈。

这项任务怎么学

对应资料：FastAPI Handling Errors、Response Status Code。

主导方法：先写预期错误表 → 主动制造输入错误和业务错误 → 对照实际状态码与响应体 → Debug 差异 → 用自己的话解释归属。

验收：至少保存一次自动校验错误和一次 HTTPException 结果；能区分“客户端输入错误”和“服务代码失败”。

内部拆分：错误与状态码阅读 0.5h；构造两类失败 1h；修正错误响应与信息边界 0.75h；记录 0.25h。

学习建议：不要一开始写全局异常体系；先让错误准确、可重复、无敏感信息，再谈抽象。

任务三：TestClient 与基础 API 测试

2.5 小时
P0API Test L1–L2

用途：把“刚才手点成功了”变成以后可以重复运行的证据，防止修改 Schema 或业务逻辑后悄悄破坏接口。

  1. 使用 TestClient 调用健康检查和 POST 接口。
  2. 为正常输入断言状态码、关键字段和响应结构。
  3. 为缺字段或非法类型断言 4xx 与错误信息。
  4. 若真实模型调用不稳定，在单元测试中用固定函数或模拟结果隔离外部依赖；保留一次真实 API 手动验证即可。

这项任务怎么学

对应资料：FastAPI Testing、pytest Get Started。

主导方法：官方最小测试 → 改成自己的端点 → 先写正常测试 → 再写异常测试 → 故意改坏一个字段确认测试会失败。

验收：至少 3 个测试：health、正常 POST、非法请求；能解释每个断言保护了什么。

内部拆分：TestClient 示例 0.5h；正常与异常测试 1.25h；故意破坏并修复 0.5h；运行说明 0.25h。

学习建议：测试重点是固定契约，不是覆盖率数字。本周不要为了“看起来专业”搭复杂 fixture。

任务四：RAG 全景与最小 Embedding / 相似度实验

4 小时
P0RAG L2 · Retrieval L1–L2

用途：理解 RAG 如何在生成前找出外部资料，把“模型凭参数回答”变成“基于检索上下文回答”。本周目标是掌握数据流，不是完成向量数据库工程。

Document→Chunk→Embedding→Vector Store→Retriever / Top-k→Context→LLM Answer
  1. 阅读 RAG 入门章节，用一句话写出每个组件输入、输出和职责。
  2. 准备 5–10 条公开或自写短文本，使用一个现成 Embedding 模型生成向量。
  3. 对一个查询计算相似度并排序，观察 Top-1 / Top-3；更换查询再比较。
  4. 画出 RAG 架构图，标清离线索引与在线查询两条路径。
  5. 记录 Chunk 太大、太小以及 Top-k 变化可能造成的影响，但本周不展开优化。

这项任务怎么学

对应资料：All-in-RAG RAG 入门、All-in-RAG Embedding 章节、Sentence Transformers Semantic Textual Similarity。

主导方法：教材建立全景 → AI 用中文检查组件边界 → 你画图 → 用极小文本集做实验 → 修改查询和 Top-k 观察结果。

验收：能闭卷解释完整 RAG 流程；代码能输出查询与相似文本排序；能说明向量库保存什么、Retriever 返回什么、Context 如何进入模型。

内部拆分：RAG 全景阅读与讲解 1h；架构图 0.75h；Embedding / 相似度实验 1.5h；Top-k 对比与记录 0.75h。

学习建议：不接 LangChain、向量数据库或复杂 PDF；先看清数据怎么流动。W08 会正式进入文档 Pipeline 与 Chunk。

任务五：整合、闭卷重写与 Gate 1 自查

3 小时
P0 验收阶段门证据

用途：确认前置阶段不是“资料看完”，而是能够独立运行、修改、解释，并判断哪些阻塞必须在进入 RAG 项目前补齐。

  1. 关闭完整答案，从空白骨架重写一个 Request / Response Schema 和 POST Route。
  2. 运行正常、非法输入与业务错误测试，保存命令和结果摘要。
  3. 闭卷画出 RAG 数据流和 Tool Calling 数据流，解释两者解决的问题。
  4. 按 Gate 1 清单逐项标记“有代码证据 / 仅能解释 / 仍阻塞”，不因排期自动宣称通过。
  5. 只把阻塞 W08 的 P0 加入补齐清单；P1 月内滚动，P2 取消。

这项任务怎么学

对应资料：自己的代码、测试输出、W04–W07 产出与本页验收清单。

主导方法：闭卷先做 → 卡住处记录 → 精准回查对应章节 → 重写或修改 → ChatGPT 提问检查解释 → Codex 检查代码与测试。

验收：可运行 API、基础测试、RAG 架构图、最小相似度实验，以及一份基于证据的 Gate 1 自查。

内部拆分：闭卷重写 API 1h；重跑测试与修复 0.75h；两张数据流图和口述 0.5h；Gate 1 证据清单 0.75h。

学习建议：“能在提示下完成”不等于独立掌握；保留卡点很有价值，它决定 W08 开始前真正需要补什么。
