P01.5h · 10%

任务 A｜W06 阻塞性自检

为什么：FastAPI 只是“把能力暴露出去”的外壳。如果你还说不清 Agent Loop 或 Tool Calling 的输入输出，API 只会把不清楚的内部逻辑包装起来。

  1. 闭卷画出：User → LLM → Tool Call → Python Tool → Tool Result → LLM → Answer。
  2. 口头解释 tool schema 为什么需要参数类型和描述。
  3. 如果上周代码未跑通，只补一个最小工具，例如 get_weather(city: str) 的模拟函数；不要扩展多工具、多 Agent。

验收：不用看资料，3 分钟解释完整 loop；能指出“模型决定调用工具”和“Python 真正执行工具”是两件不同的事。

P04.5h · 30%

任务 B｜FastAPI 最小工程闭环

要解决的问题：把“本地函数”变成“别人可以通过 HTTP 调用的服务”。重点只抓 W07 原计划列出的 Request、Response、Schema、Exception。

  1. 先理解 30–40 分钟：route、POST、request body、response、status code 分别是什么。
  2. 最小跟做：建立 app = FastAPI()，跑通 uvicorn，打开 /docs。
  3. Pydantic Schema：为请求写 BaseModel；故意传错类型，观察自动校验错误。
  4. Response：定义返回模型，理解为什么输出也需要数据契约。
  5. Exception：主动制造一个不存在资源 / 非法参数错误，用 HTTPException 返回明确状态码。

学习方法：文档只看本周需要的页面；每看一个概念立刻改代码。不要先把 FastAPI 教程从头看完。

验收：从空文件开始，20–30 分钟内能独立写出一个 POST endpoint；Swagger UI 能成功请求；错误输入不会悄悄吞掉。

P03.0h · 20%

任务 C｜RAG 全景：先理解系统，不急着堆框架

本周只需要形成下面这条链：

Document→Chunk→Embedding→Vector DB→Retriever→Context→LLM
  1. 用自己的话解释每个组件“输入是什么、输出是什么、解决什么问题”。
  2. 尤其分清：Embedding 负责表示，Vector DB 负责存储/搜索，Retriever 负责取回候选内容。
  3. 知道 chunk 太大 / 太小会影响检索，但本周不深入 chunk 策略实验。
  4. 知道“大 Context Window”不等于 RAG 自动失去价值：工程上仍要考虑成本、数据规模、更新频率和检索精度。

验收：给你一份 PDF 知识库场景，你能不看资料画出 RAG 流程，并说明 query 从哪里进入、检索结果如何进入最终 Prompt。

  2. service.py 先允许使用简单 mock / 已有 LLM API；不要求本周就接完整向量库。

验收：运行命令、请求示例和结构写入 README；你能解释为什么 API 层、schema 层、AI service 层要分开。
