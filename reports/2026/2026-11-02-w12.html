1｜评测目标与 Golden Set

3h

Golden Set（黄金测试集）是一组人工确认过输入和期望行为的固定用例。它不是“所有真实问题”，而是当前系统最重要、最容易失败、能稳定复跑的一小组代表。

为什么要学：没有固定输入和真值，W10 与 W11 的差异无法公平比较；查询一变、标注一变，分数就失去意义。它也是 W21 更系统的 Golden Dataset 的最小前置。

先定义评测契约

from dataclasses import dataclass

@dataclass(frozen=True)
class GoldenCase:
    case_id: str
    query: str
    relevant_chunk_ids: tuple[str, ...]
    required_facts: tuple[str, ...]
    category: str

CASES = [
    GoldenCase(
        case_id="refund-001",
        query="退款申请后多久原路退回？",
        relevant_chunk_ids=("policy-refund-time",),
        required_facts=("3到5个工作日", "原支付渠道"),
        category="single-hop",
    )
]
字段含义：relevant_chunk_ids回答“应该检索到什么”；required_facts回答“最终回答至少应包含什么”。不要把完整参考答案当作唯一字符串真值，否则措辞变化会被误判。

常见错误 → 原因 → 正确写法

  • 错误：只存 query 和一段参考答案。原因：无法区分检索失败还是生成失败。改正：同时存相关 Chunk ID 与必需事实。
  • 错误：用当前系统输出反过来当真值。原因：会把已有错误写入标注。改正：回看原文，由人确认。
  • 错误：每次运行前临时改 expected。原因：版本不可比较。改正：修改时记录 dataset_version 和理由。

2｜Retrieval Evaluation：Hit、Precision、Recall、MRR

3h

检索评测（Retrieval Evaluation）只看返回的 Chunk 排名，不看模型最后怎么组织答案。设前 k 个结果为 retrieved，人工标注的相关集合为 relevant：

  • Hit@k：前 k 个里只要出现至少一个相关 Chunk 就记 1，适合“找到一个证据就够”的场景。
  • Precision@k：前 k 个中相关项占比，衡量上下文有多少噪声。
  • Recall@k：前 k 个找回了全部相关项的多少比例，适合答案分散在多段的场景。
  • MRR（Mean Reciprocal Rank，平均倒数排名）：第一个相关结果越靠前越高；单条为 1 / rank，未命中为 0。
def retrieval_metrics(
    retrieved_ids: list[str],
    relevant_ids: tuple[str, ...],
    k: int,
) -> dict[str, float]:
    if k <= 0:
        raise ValueError("k must be positive")
    top_k = retrieved_ids[:k]
    relevant = set(relevant_ids)
    if not relevant:
        raise ValueError("relevant_ids must not be empty")

    matched = [chunk_id for chunk_id in top_k if chunk_id in relevant]
    first_rank = next(
        (rank for rank, chunk_id in enumerate(top_k, start=1)
         if chunk_id in relevant),
        None,
    )
    return {
        "hit_at_k": float(bool(matched)),
        "precision_at_k": len(matched) / k,
        "recall_at_k": len(set(matched)) / len(relevant),
        "reciprocal_rank": 0.0 if first_rank is None else 1 / first_rank,
    }
指标陷阱：如果 Retriever 实际只返回 2 条，却用 k=5 计算 len(matched)/5，Precision@5 会包含“未返回位置”的惩罚。先约定系统必须返回 k 条，或明确采用 len(top_k) 作为分母；报告中不可混用。

3｜Answer Evaluation：事实、引用与人工量表

3h

回答评测（Answer Evaluation）判断最终答案是否满足任务。开放式中文回答不适合只做 exact match：同一事实可以有多种正确表达。本周采用三层证据：

  1. 事实覆盖率（Fact Coverage）：必需事实有多少被答案明确包含；第一版用规范化关键词/短语，承认它只是一种近似。
  2. 引用正确性（Citation Correctness）：回答引用的 Chunk 是否都在实际检索上下文中，且至少包含人工标注相关 Chunk。
  3. 人工量表（Human Rubric）：对正确性、完整性、忠实性分别给 0/1/2，并写失败原因。
from dataclasses import dataclass

@dataclass(frozen=True)
class AnswerScore:
    fact_coverage: float
    citations_valid: bool
    human_correctness: int | None = None
    failure_note: str | None = None

def fact_coverage(answer: str, required_facts: tuple[str, ...]) -> float:
    if not required_facts:
        raise ValueError("required_facts must not be empty")
    normalized = "".join(answer.lower().split())
    hits = sum(
        "".join(fact.lower().split()) in normalized
        for fact in required_facts
    )
    return hits / len(required_facts)

def citations_valid(
    cited_ids: list[str],
    retrieved_ids: list[str],
) -> bool:
    return bool(cited_ids) and set(cited_ids).issubset(set(retrieved_ids))

错误示例

# 错误：把“关键词全出现”直接等同于答案正确
passed = fact_coverage(answer, required_facts) == 1.0

为什么错：“不是 3 到 5 个工作日”也包含关键词；模型还可能把事实关系说反。正确做法是将自动事实覆盖率作为筛查信号，再对小数据集做人工正确性/忠实性确认。

4｜批量执行、异常隔离与结果版本

2.5h

批量评测（Batch Evaluation）把每个 GoldenCase 送入同一 RAG Pipeline，并逐条保存输入、配置、检索结果、回答、指标和错误。一个用例失败不能让整批结果消失。

import json
from pathlib import Path
from typing import Callable

def run_case(case: GoldenCase, rag: Callable[[str], dict]) -> dict:
    try:
        output = rag(case.query)
        metrics = retrieval_metrics(
            output["retrieved_ids"],
            case.relevant_chunk_ids,
            k=3,
        )
        return {
            "case_id": case.case_id,
            "status": "ok",
            "answer": output["answer"],
            "retrieved_ids": output["retrieved_ids"],
            **metrics,
        }
    except Exception as exc:
        return {
            "case_id": case.case_id,
            "status": "error",
            "error_type": type(exc).__name__,
            "error_message": str(exc),
        }

def write_jsonl(path: Path, rows: list[dict]) -> None:
    with path.open("w", encoding="utf-8") as file:
        for row in rows:
            file.write(json.dumps(row, ensure_ascii=False) + "\n")
每次运行必须附带：dataset_version、pipeline_version、embedding / generation 模型标识、top_k、是否 rerank、时间戳。否则几天后无法知道两个结果文件为何不同。

5｜Latency、Token Usage 与 Cost

1.5h

延迟（Latency）回答“用户等多久”；Token Usage回答“本次输入/输出量多大”；Cost是基于供应商当前价格的估算。三者必须和质量指标一起看。

from time import perf_counter

def measured_call(call_model):
    started = perf_counter()
    response = call_model()
    latency_ms = (perf_counter() - started) * 1000

    # 适配实际供应商响应；不要猜字段
    input_tokens = response.usage.input_tokens
    output_tokens = response.usage.output_tokens
    return response, {
        "latency_ms": round(latency_ms, 1),
        "input_tokens": input_tokens,
        "output_tokens": output_tokens,
    }

def estimate_cost(
    input_tokens: int,
    output_tokens: int,
    input_price_per_million: float,
    output_price_per_million: float,
) -> float:
    return (
        input_tokens * input_price_per_million
        + output_tokens * output_price_per_million
    ) / 1_000_000
  • 用 perf_counter() 计算时间差；不要用墙上时间做短耗时测量。
  • 价格放配置并记录日期，不要硬编码成“永久价格”。
  • 分别记录 retrieval、rerank、generation；只记录总耗时会遮住瓶颈。
  • 至少报告平均值与最大值；样本少时不要伪装成稳定的生产 P95。

边界测试

缓存命中与未命中、模型调用重试、usage 缺失、免费/本地模型、输入 0 Token、价格配置为负数。若响应没有 usage，写 null 并说明，不可填 0 冒充真实。

6｜Baseline 报告、失败分类与闭卷重写

3h

Baseline Report（基线报告）不是展示漂亮平均分，而是记录一个可复测版本的表现和限制。最少比较 W10 vector baseline 与 W11 vector + rerank：

版本Hit@3Recall@3MRR答案事实覆盖平均延迟估算成本
vector-baseline待运行待运行待运行待人工复核待运行待配置
vector-rerank待运行待运行待运行待人工复核待运行待配置

失败分类

  • dataset：标注错误、问题歧义、知识库无答案。
  • retrieval：相关 Chunk 未进入 top-k。
  • ranking：相关 Chunk 已召回但排序太低。
  • generation：上下文已有证据，但回答遗漏、误读或幻觉。
  • system：超时、限流、解析失败、空响应。

闭卷重写

  1. 关闭页面，重写 GoldenCase 与 retrieval_metrics()。
  2. 用一个三结果案例手算 Precision@3、Recall@3、RR。
  3. 重写逐条异常隔离的 run_case()。
  4. 画出 Dataset → Pipeline → Per-case Result → Aggregate → Report。
  5. 口述一个“检索命中但答案错误”的 Debug 顺序。

完成点：报告必须包含版本配置、逐项指标、至少 3 个失败案例、质量/延迟/成本权衡，以及“保留、回退或继续实验”的明确结论。

  3. 为什么开放式回答不能只用 exact match？
  4. 关键词全命中为什么仍不能证明答案正确？
